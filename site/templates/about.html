what tianguis is

tianguis is a Nim package registry. it indexes the canonical name → source mapping for the Nim ecosystem, with three commitments that distinguish it from nimble + nim-lang/packages:

content-addressed identity

every version in tianguis carries a sha256 of its source tree, computed by a deterministic algorithm (sorted entries, zero mtime, executable-bit-preserving). fetch a package, recompute the hash, compare. mismatch = tampered bytes.

this matters because URL-based registries (nim-lang/packages, today's pypi pre-PEP 740, pre-Sigstore-NPM) trust that the bytes at https://github.com/x/y at tag v1.0 are the same bytes everyone else saw. force-pushes, mirror compromises, upstream account takeovers all silently substitute content. content-addressed identity makes that detectable.

Sigstore attestation

every entry in tianguis is signed via Sigstore (keyless cosign via OIDC). attestations land in Rekor's transparency log under one of two identities:

  • author-signed — the package author published via milpa publish from their own CI. Sigstore cert subject = their workflow identity.
  • milpa-vendored — the vendor-en-absentia bot mirrored a nim-lang/packages entry on the author's behalf. cert subject = the milpa-bot workflow identity.

consumers can require a minimum attestation level via verification { min_attestation "author-signed" } in milpa.kdl, refusing vendored entries for security-sensitive deps.

no human merges on the publishing path

the publishing flow is entirely automated. an author tags a release in their repo → milpa publish packs source, pushes OCI, cosign-signs, POSTs the tianguis dispatch endpoint → a workflow on the tianguis repo verifies + commits the index entry. end-to-end: ~60 seconds. zero human review steps. zero curation latency.

nim-lang/packages routinely sits with PRs open for days or weeks. tianguis eliminates that channel by inverting the trust model: rather than humans gatekeeping submissions, machines verify cryptographic attestations.

what tianguis is not

  • not a dep resolver. that's milpa. tianguis just provides the name → version → bytes mapping milpa consumes.
  • not a backend service. the registry is a static GH Pages site; index.kdl + index.json served as files. the dispatch endpoint exists only to gate publish events, never to serve package data.
  • not a fork of nim-lang/packages. tianguis is a different model entirely. it does, however, vendor-en-absentia from nim-lang/packages so the existing ecosystem is immediately usable.

federation

tianguis is one possible registry, not the only one. consumers can configure milpa with a list of index URLs via MILPA_INDEX_URLS or a manifest setting. an organization can run its own private registry by hosting an index.kdl on any HTTP server.

the index format is specified in spec. nothing about milpa requires tianguis specifically — it's the default, not the law.
