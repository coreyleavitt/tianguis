what tianguis specifies

tianguis is a Nim package registry, but more precisely it's three small specifications layered to produce one cohesive trust model. each layer is independently implementable and independently verifiable. nothing about the design requires the specific software running at tianguis.dev — a conformant implementation in any language could host an equivalent registry, and milpa would consume it the same way.

this page walks each layer in narrative form. the deep-dive references at the bottom of each section have the normative grammars and error catalogs.

  • 1. the data format — what an index file is
  • 2. the distribution model — how the index reaches consumers
  • 3. the attestation model — what makes any of it trustworthy
  • reference implementations + tools

1 the data format

the registry is one file: index.kdl. it's plain text, parseable in a few hundred lines, hand-editable, strict-schema. every published version of every package is one node. there is no database, no API, no caching layer between the index and its consumers.

every index.kdl has an auto-derived JSON projection (index.json) emitted by the same tool. the two are bijective — semantic round-trip is enforced in CI via tianguis project --check. consumers may parse either; KDL is canonical because it's the human-editable form.

example

schema_version 1
package "nimkdl" {
    namespace "coreyleavitt"
    upstream (url)"https://github.com/coreyleavitt/nimkdl"
    version "0.1.4" {
        content_hash "sha256:1aaf2a95f53681c8…"
        provenance {
            kind "oci"
            registry "ghcr.io"
            repository "coreyleavitt/nimkdl"
            digest "sha256:e51aab085ef4f58e…"
        }
        attestation "author-signed"
        signed_by "https://github.com/coreyleavitt/tianguis/.github/workflows/publish.yaml"
        published_at "2026-05-26T04:49:44Z"
    }
}

every field above is required (or deliberately optional with a documented default). unknown nodes or properties are rejected with stable error codes from the IDX-* catalog. that's an unusual choice — most registries lean permissive — but it serves the multi-implementation goal: an implementer who emits a field tianguis-the-reference doesn't recognize gets a loud error, not silent divergence.

canonical ordering is also part of the format, not the implementation: packages sort alphabetically, versions sort descending-semver, requires keys sort alphabetically. this means the rendered file diffs cleanly across vendor passes and author publishes regardless of which tool produced the input.

→ deep dive: index-format.md — full normative grammar, JSON projection rules, the strict-schema error catalog.

2 the distribution model

there are two URLs anyone needs to know: 

https://tianguis.dev/index.kdl       # canonical registry (this site serves it)
https://dispatch.tianguis.dev/v1/publish   # author-side POST endpoint (Scaleway function)

tianguis.dev is GitHub Pages serving static files generated from the index — no backend, no database, no rate limiting beyond GH's edge cache. dispatch.tianguis.dev exists only to accept publish events from authors' CI; it never serves package data and never performs cryptographic decisions (more on that in layer 3).

consumers fetch /index.kdl over HTTPS, cache it locally with a configurable TTL, and refresh on a stale-while-revalidate basis. that's the entire distribution protocol on the consumer side. a private registry is a private GH Pages site (or any other static host) serving an index.kdl of the same shape; milpa supports a list of registries via MILPA_INDEX_URLS for federation.

the publish flow

     ┌─────────────────────┐
     │  author repo CI     │   tags v1.0.0 → publish workflow:
     │  (GH, GitLab, etc.) │   pack source · push OCI · cosign sign
     └──────────┬──────────┘
                │  POST + OIDC bearer
                ▼
     ┌─────────────────────┐
     │  dispatch endpoint  │   verify OIDC · identity cross-check
     │  (Scaleway, Go)     │   → workflow_dispatch to commit-entry
     └──────────┬──────────┘
                │  GH App installation token
                ▼
     ┌─────────────────────┐
     │  commit workflow    │   cosign verify · oras pull
     │  (GH Actions, Nim)  │   tianguis add-entry · cosign attest
     │                     │   git push to main
     └──────────┬──────────┘
                │
                ▼
     ┌─────────────────────┐
     │   pages workflow    │   regenerate site + index.kdl/json
     │   → tianguis.dev    │   live within seconds
     └─────────────────────┘

total latency: about a minute from tag push to live registry entry. no human review at any point. the only humans involved are the author tagging their release and (later) consumers fetching their package.

3 the attestation model

the data format is just bytes; the distribution model is just HTTP. neither tells you whether to trust an entry. that's the third layer, and it's the most important.

every published version of every package has three different hashes involved in its trust chain. they're not interchangeable; each answers a different question:

hashexamplewhat it's a SHA256 ofwho computes it
content_hash sha256:1aaf2a95… the unpacked source tree, by milpa's identity algorithm milpa (publisher and consumer both)
OCI digest sha256:e51aab08… the OCI manifest JSON the OCI registry
Rekor hash sha256:a4ded9d7… cosign's "claim" payload (which references the OCI digest) cosign at sign time

each is computed independently. each is verifiable independently. and they fit together such that no single party — not the author, not tianguis, not the OCI registry, not Sigstore — can silently substitute content without at least one of the three failing to verify.

what's trusted where

  • the author's CI OIDC identity is the bottom turtle. compromise of the author's CI (or signing-key-equivalent) is indistinguishable from the author publishing. no registry can mitigate this.
  • cosign + Sigstore Fulcio + Rekor are the cryptographic substrate. compromise of Sigstore is a global supply-chain event; we accept this dependency.
  • tianguis dispatch is NOT in the trust chain. it only verifies the OIDC token enough to filter spam and triggers the commit workflow. a fully-compromised dispatch can spam workflow runs but cannot inject false entries (the commit workflow re-verifies everything cryptographically).
  • the OCI registry stores bytes. tampering is detected: the OCI digest is pinned in the index, cosign's signature is over a payload that references that digest, and milpa's content_hash recomputation catches any byte change.
  • third-party verifiability: every index commit corresponds to a Rekor attestation under the tianguis commit workflow's GH Actions identity. independent monitors can compare what's in index.kdl against what Rekor records and flag divergence publicly.

two attestation levels

the attestation field in each version distinguishes how the entry got into the index:

  • author-signed — the author published via milpa publish. cosign signer identity is their CI's workflow. strongest attestation level; consumers who want maximum integrity can require it via verification { min_attestation "author-signed" } in milpa.kdl.
  • milpa-vendored — the vendor-en-absentia bot mirrored a nim-lang/packages entry on the author's behalf. cosign signer identity is the milpa-bot workflow. weaker attestation (the author wasn't involved) but still cryptographically attributable.

authors who later adopt milpa publish for a previously-vendored package get precedence — new versions land as author-signed; vendor-bot stops contributing to that package. old vendored entries remain resolvable so existing lockfiles don't break.

→ deep dive: the distribution + publishing RFC (in-repo) covers the trust model in normative detail. for the live verification UI: every per-version block on this site has a view in Rekor link + a copy-paste cosign verify command.

reference implementations + tools

tianguis isn't a single piece of software — it's a small protocol with multiple cooperating implementations. these are the load-bearing pieces today:

milpa
the consumer-side resolver + fetcher. Python today (design vehicle); Rust + Nim ports planned. consumes index.kdl, resolves named deps, pulls via OCI, verifies content_hash. publishing via milpa publish.
tianguis
this registry. Go dispatch endpoint (Scaleway) + Nim vendor-bot + Python site builder + GH Actions workflows for the commit + attestation pipeline.
cosign
Sigstore's CLI for keyless signing + verification. milpa publish shells to it; the commit workflow shells to it. all crypto is delegated here — we don't reimplement.
oras
the OCI artifact CLI. used by milpa publish to push source tarballs, used by the commit workflow to pull them back for verification.
KDL
the canonical encoding for index.kdl and milpa.kdl. v2 grammar; we use the Python parser and our own Nim parser.
